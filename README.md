# 本地乱序指令流水线模拟器（Go）

`pipeline` 包是一个完全本地、自包含的乱序（out-of-order）指令流水线
模拟器。它从内存中按程序顺序排列的静态指令序列出发，在**不改变程序语义**
的前提下动态识别寄存器数据相关、内存地址相关与控制相关，按操作数可用
顺序乱序执行，并保证所有架构更新严格按程序顺序提交；在分支误预测、
精确异常/中断以及注入故障时原子地恢复到确定的一致状态。

无外部设备、无网络、不确定随机源，相同程序 + 相同 `Config.Seed` 下
调度轨迹与提交轨迹逐条一致，可用于离线回放与历史复现。

## 快速开始

```go
cfg := pipeline.DefaultConfig()
prog := []pipeline.Instruction{
    {Kind: pipeline.OpALU, ALU: pipeline.ALUAdd, Rd: 1, Imm: 5},
    {Kind: pipeline.OpALU, ALU: pipeline.ALUAdd, Rd: 2, Rs1: 1, Imm: 3},
}
st := pipeline.New(prog, cfg).Run()
st.Registers[1] // 5
st.Registers[2] // 8
```

运行测试：

```sh
go test ./...
```

## 指令集

| Kind      | 含义                       | 说明                                           |
|-----------|----------------------------|------------------------------------------------|
| `OpALU`   | 整数寄存器运算             | `ALU` 选择 +,-,&,\|,^,<<,>>,< ；`ADD` 兼作 ADDI（`a+b+Imm`） |
| `OpLoad`  | 内存读                     | 地址 `Rs1 + Imm`，结果写 `Rd`                  |
| `OpStore` | 内存写                     | 地址 `Rs1 + Imm`，数据来自 `Rs2`               |
| `OpBranch`| 条件分支                   | `Branch` 选择 ==,!=,<,>=,!=0；目标 `Target`    |
| `OpJump`  | 无条件跳转                 | 目标 `Target`                                  |
| `OpTrap`  | 精确异常                   | `TrapCode` 给出异常原因                        |

`Seq` 与 `PC` 是程序的位置属性（连续 4 字节字），由 `New` 按数组下标
统一编号，调用方无需填写；store/branch/jump/trap 的 `Rd` 会被规范化为
-1（不写寄存器）。无寄存器操作数用 -1 表示。

## 微体系结构

每个时钟周期依次执行：完成/写回 → 提交 → 取指/重命名 → 发射。

- **取指与预测**：取指宽度等于发射宽度。条件分支经
  （可关闭的）2 位饱和计数器预测器预测方向并据此提前取指；跳转
  必定重定向。预测结果记录在 ROB 表项中。
- **寄存器重命名**：每个逻辑寄存器映射到一个物理寄存器；ROB 每槽
  额外提供一个可分配物理寄存器。重命名记录旧映射，squash 时按 LIFO
  精确还原，因此同一逻辑寄存器的不同版本既不丢更新也不会读到陈旧值。
  RAT 维护 `物理寄存器 -> 在飞生产者 Tag`，发射窗口据此判断 RAW；
  WAW/WAR 由重命名天然消解。
- **乱序发射**：发射窗口在每个周期选择操作数全部就绪的指令，按 Tag
  （程序序）确定性排序，受发射宽度限制。各指令类别有可配置延迟。
- **写回**：结果写入物理寄存器并向所有等待者广播；未提交结果只存在
  于物理寄存器与 ROB 中，**不更新架构寄存器/内存**，故后续读取在提交
  前观察不到。
- **顺序提交**：ROB 头部就绪才提交，更新架构寄存器/数据内存，释放旧
  物理映射。提交轨迹严格按程序序出现。

## 内存排序与地址相关

访存操作进入按程序序排列的 load/store 队列。Store 在提交前**绝不写
内存**，因此 WAW/WAR 由顺序提交天然保证；load 通过“最近的更老同地址
已就绪 store 前递”获得 RAW 值。

地址未知时采用可配置的保守策略 `Config.UnknownPolicy`：

- `PolicyStall`（默认）：只要存在地址未知的更老 store，较年轻的
  load/store 一律等待——始终安全、可复现。
- `PolicyAssumeAlias`：允许 load 在更老 store 地址未知时投机执行；
  当该 store 之后解析出相同地址时，触发内存序违例重放，把 load 及其
  后继 squash 并重新执行。

地址未按 `Config.MemoryGranularity` 对齐时产生精确的
load/store 地址异常。

## 精确恢复语义

`Status.LastRecovery` / `RecoveryPoint()` 返回最近一次恢复的
周期、指令序号、恢复 PC 与原因（`ExceptionCode`）。

- **分支误预测**：分支在执行期解析真实方向/目标；若与预测不符，
  分支本身解析后正常提交，**仅**撤销更年轻的错误路径指令，RAT/LIFO
  回滚，取指重定向到正确 PC。错误路径指令不会提交。
- **精确异常**（trap、非法、地址异常）：异常指令**之前**的提交全部
  保留；异常指令及其后所有未提交指令原子地不可见（无部分写入），
  机器停在异常 PC，原因与位置可查询。
- **精确中断**：在提交边界取得。已完成的更老指令先提交，随后在
  下一条未提交指令前原子排空流水线并停机。

所有恢复都不动已提交架构状态（store 仅在提交时写内存），因此恢复点
天然一致。

## 故障注入

```go
p.InjectFault(pipeline.FaultSpec{Kind: pipeline.FaultFlushAndRestart, Seq: 3})
```

- `FaultFlushAndRestart`：在指令执行点击发一次，把它及更年轻的在飞
  工作全部撤销并从该指令重新取指，效果等同于一次误预测。
- `FaultDropResult`：丢弃该指令的一次写回，强制其重新执行。

故障是**单发**的（重放不会重复触发）。恢复后的最终提交状态、架构
寄存器与内存映像与未注入故障的完整执行**完全一致**；仅提交周期可能
因重放而后移。

## 确定性与回放

调度器的就绪选择按 Tag 排序，预测器初始状态由 `Config.Seed` 经一个
内置 xorshift PRG 播种；所有时序与决策都是纯函数式的。`Trace` 同时
记录调度事件（`SchedulingTrace`）与提交记录（`CommitTrace`）。

```go
err := pipeline.Replay(prog, cfg, recordedTrace, faults)
```

相同程序、配置（含种子）与故障计划两次运行得到逐字节相同的轨迹；
不同种子允许调度不同，但架构结果必须相同。

## 包结构

| 文件             | 职责                                            |
|------------------|-------------------------------------------------|
| `types.go`       | 指令、配置、异常码、事件等共享类型               |
| `pipeline.go`    | 流水线主体：取指/重命名/发射/执行/提交/恢复       |
| `rename.go`      | RAT、物理寄存器空闲链表、生产者映射              |
| `rob.go`         | 循环重排序缓冲（Tag 全局单调，locator 定位槽位）  |
| `scheduler.go`   | 发射窗口、操作数就绪与确定性选择                  |
| `memory.go`      | 数据内存、load/store 队列与地址相关检测           |
| `predictor.go`   | 2 位饱和计数器分支预测器                         |
| `faults.go`      | 故障注入规约                                     |
| `trace.go`       | 轨迹记录、等价比较与 `Replay`                    |
| `rng.go`         | 确定性随机源                                     |
